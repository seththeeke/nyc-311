# Agent Orchestration — spec

> **Status: Phase 1 built — 2026-11-07.** Reworked from the
> 2026-09-27 spec (a full scheduler replacing launchd, never built) into a
> phased plan. Phase 1 is a brute-force, **read-only** monitor over the agents
> as they run today; Phases 2–3 grow it toward the original north star. The
> 2026-09-27 decisions that still hold are kept in §7 as Phase 3 design.

## 1. What this is

`agent-web-app/` — a small, **localhost-only** app (one npm package: a local
Node server plus a React UI) for keeping tabs on the agents running on the
Mac mini. It's built in phases:

| Phase | Scope | Scheduler |
|---|---|---|
| **1 (now)** | **Read-only monitor**: what's installed, what ran, what's running, what broke | launchd, unchanged |
| 2 | Actions over launchd: Run now, pause/resume, (re)install | launchd |
| 3 (north star) | The app owns scheduling and runs; launchd retired | the app |

Each phase builds on the last: same package, same layering, same UI. What
changes between phases is the **run source** (§4.2) and new action endpoints,
not the structure.

### Principles

- **localhost only.** Binds `127.0.0.1`, never deployed, never part of the
  pipeline (§6).
- **Brute force is fine.** It's a personal tool on one machine; Phase 1 reads
  logs and shells out to `launchctl`/`git` rather than building anything
  clever. Expect rework as it grows — don't gold-plate.
- **It never defines agent behavior.** Agents, prompts, permissions and run
  rules live where they live today (§2). The app reads them; later it
  triggers them; it never re-implements them.
- **Phase 1 never changes anything.** No buttons that start, stop, install or
  edit. Agent runs are started by launchd or by the user in a terminal.

## 2. How the agents actually run today (2026-11-07)

Eight agents (2026-11-07), scheduled by **launchd** on the Mac mini
(`docs/agent-automation-setup.md`). Their live config is the app's own
dashboard; this section describes the shape, not the current values, which
change often.

- **`KIND`** picks the mode: `pr-limit` (default; NEW or REVISE by the count
  of open `BRANCH_PREFIX` PRs against `MAX_OPEN_PRS`), `assigned-issue`
  (RESUME, REVISE, NEW or IDLE from the agent's labelled issues) or
  `operations` (one run per fire).
- **`SCHEDULE`** is space-separated slots, `[Day@]HH:MM[=MODE]`: `Day` is
  Sun..Sat (omitted = daily) and `MODE` an ALL_CAPS slot mode (e.g.
  `05:00=AUDIT 08:00=CONVERSE`) that picks `PROMPT_<MODE>` and
  `MODEL_<MODE>`.
- **Flags**: `MODEL`, `TEAM_CHAT_ENV`, `OPS_TOOLS`, `PRODUCT_TOOLS`,
  `MEMORY`, `REPORTS`, `USAGE_SUMMARY`.

The run path:

1. **launchd** fires `~/Library/LaunchAgents/com.nyc311.agent.<agent>.plist`,
   generated by `scripts/agent-schedule-install.sh` from `SCHEDULE` in
   `scripts/agent-schedules/<agent>.env`. It runs
   `/bin/sh <checkout>/scripts/agent-scheduled-run.sh <agent>`, where
   `<checkout>` must be the **scheduler clone `~/agents/nyc-311`** — launchd
   can't read `~/Documents` (TCC), and a plist pointing there fails every run
   with `Operation not permitted` (exit 126) into `launchd.log` (2026-11-05).
2. **`agent-scheduled-run.sh`** fast-forwards the clone (npm ci on lockfile
   changes, re-exec on self-update), reads the `.env` from `origin/main`,
   takes a per-agent lock (`<logdir>/.run.lock/pid`; a second run while one
   holds it logs "another … run … is in progress — skipping"), picks the mode,
   then calls:
3. **`agent-worktree.sh run <agent> "<prompt>"`** — a fresh detached worktree
   of `origin/main` under `~/agents/nyc-311-worktrees/`, Team Chat (and
   ops/product MCP) config per run, `claude --agent <agent> -p`, then removes
   the worktree unless the run failed or left changes. With `MEMORY=1` it
   commits the agent's memory file to main afterwards.

**Outputs** (the Phase 1 data source), per agent, under
`~/Library/Logs/nyc311-agents/<agent>/` (`AGENT_LOG_ROOT` overrides):

| File | Content |
|---|---|
| `launchd.log` | launchd's stdout/stderr — empty when healthy; anything here means the job couldn't start |
| `<YYYYMMDDTHHMMSS>.log` | one per run: timestamped `[YYYY-MM-DD HH:MM:SS] …` lines from the runner, agent-worktree's lines, then the agent's final report |
| `<ts>.report.md` | the agent's final report alone |
| `.run.lock/pid` | present while a run is in progress |

Structured runner lines seen in real logs (the parser keys on these):

```
=== <agent> scheduled run (log: …)
primary fast-forwarded <sha>..<sha>
lockfile changed in <pkg> — npm ci
WARN: <anything>
config + prompts from origin/main @ <sha>
open devx/* PRs: 2 (#158 #160), limit 3 → NEW mode       (pr-limit / assigned-issue)
nothing assigned to <agent> needs work — not starting claude (IDLE)
operations run → RUN (model opus)                          (operations; slot mode or RUN, model optional)
another <agent> run (pid N) is in progress — skipping
agent exited <code> after <Xm Ys> — final report:
team-chat: <chat post id …>                                (from the report's "Chat post:" line)
open devx/* PRs after run: #158 #160 | none
=== done (<MODE>, exit <code>)
```

Logs older than 30 days and kept worktrees older than 7 days are pruned by the
runner itself.

## 3. Phase 1 — read-only monitor

### 3.1 Pages

- **Dashboard** — one card per agent: health badge, schedule, next fire,
  last run (status, mode, when, duration), and "running now" with elapsed
  time. A banner lists anything unhealthy (§3.2).
- **Agent** — the agent's config (`.env` values minus prompts' long text, its
  description from `.claude/agents/<agent>.md`), install state, and run
  history (newest first).
- **Run** — parsed summary (status, mode, exit code, duration, PRs before and
  after, chat post id, warnings), the report rendered as markdown, and the raw
  log. While `RUNNING`, the log tails (poll every 2 s).
- **Pixel Office** (`/office`) — the same agents as 8-bit rooms, one per
  persona (Pip's workshop, Celestine's sanctum, Brogan's forge, Rex's
  hangar, Penny's 1950s office, Grimble's toll bridge, Sable's office, Kid
  Kestrel's rooftop; a server closet for an agent with no persona). Each
  room is drawn in code on a 160×112 canvas at 8 fps and shows the agent's
  state: at work during a run, an alarm on an error, asleep with the lights
  off when not scheduled, idle otherwise. Windows follow the local clock.
  Under reduced motion each room holds one frame. Views are switched from a
  left sidebar.
- **Worktrees** — `git worktree list` for both checkouts: path, branch,
  dirty count, age; highlights hand-run leftovers that nothing will prune.

### 3.2 Health checks (each one a past incident)

| Check | Why |
|---|---|
| Plist missing, or not loaded in launchd | paused or never installed |
| Plist's script path isn't under the scheduler clone, or is under `~/Documents` | 2026-11-05: runs failed silently for a day |
| `launchd.log` non-empty since the last run | the job couldn't start (exit 126 etc.) |
| Plist times differ from `SCHEDULE` in the clone's `.env` | edited the schedule, forgot to reinstall |
| Last run `FAILED`, or no run when one was due | the agent is broken or launchd didn't fire |
| A run log contains `WARN:` | e.g. `git pull --ff-only failed` in the clone |
| Lock held by a dead pid | stale lock (the runner reclaims it, but worth seeing) |
| Scheduler clone dirty or not on `main` | the runner stops updating it |

### 3.3 Run status

Derived per run log (ALL_CAPS per CLAUDE.md §6, same set as Phase 3):

| Status | Rule |
|---|---|
| `RUNNING` | the agent's newest log, no `=== done` line, lock pid alive |
| `SUCCEEDED` | `=== done (…, exit 0)` |
| `FAILED` | `=== done (…, exit N)` with N ≠ 0 |
| `SKIPPED` | "is in progress — skipping", or mode `IDLE` |
| `ABORTED` | no `=== done` line and not running (killed, crashed, machine slept) |

Mode is free-form, from the mode or `done` line: `NEW`, `REVISE`,
`RESUME`, `IDLE`, `RUN` or a slot mode such as `AUDIT`. Parsing is lenient: an unrecognized line is kept in the raw log and
ignored, never an error — the runner's output will drift.

### 3.4 API (`/api`, JSON, every response zod-validated)

| Method + path | Returns |
|---|---|
| `GET /health` | server up, paths in use (log root, scheduler clone, LaunchAgents dir) |
| `GET /agents` | every agent with a `.env`: config, install/launchd state, health findings, next fire, last run, running run |
| `GET /agents/:agent` | one agent, as above |
| `GET /agents/:agent/runs?limit=` | run summaries, newest first |
| `GET /agents/:agent/runs/:runId` | summary + report markdown |
| `GET /agents/:agent/runs/:runId/log?offset=` | raw log bytes from `offset`, plus the new offset (live tail) |
| `GET /worktrees` | worktrees in both checkouts |

`runId` is the log's timestamp (`20261107T140004`). No mutating routes exist
in Phase 1, so there's nothing to guard yet beyond binding `127.0.0.1`.

### 3.5 Where it reads from

Everything comes from the machine, nothing from AWS or GitHub:

| Source | How |
|---|---|
| Agent configs | `<scheduler clone>/scripts/agent-schedules/*.env` (parsed as `KEY=value`, never `source`d — prompts contain `$(date …)`) |
| Agent descriptions | `.claude/agents/<agent>.md` frontmatter |
| Installed jobs | `~/Library/LaunchAgents/com.nyc311.agent.*.plist` (`plutil -convert json`) |
| Loaded jobs | `launchctl print gui/<uid>/com.nyc311.agent.<agent>` (state, last exit code, runs) |
| Runs | the log dir (§2) |
| Running | `.run.lock/pid` + `kill -0` |
| Worktrees | `git worktree list --porcelain` in each checkout |

Paths default to today's (`~/agents/nyc-311`, `~/Library/Logs/nyc311-agents`,
`~/Library/LaunchAgents`) and are overridable by env, which is how tests point
it at `test-data/` fixtures. The server runs from a terminal (`npm start`),
which can read `~/Documents` and `~/Library`, so it can live in either
checkout.

## 4. Building blocks that carry forward

### 4.1 Layout

The package layout is final from Phase 1, defined in root `CLAUDE.md` §5.5
(no package-level CLAUDE.md): `shared/models` (zod + TS type per
entity, used by server and UI), `server/` (controller → service → source),
`web/` (same rules as `web-app/`), `tests/` mirroring all three.

### 4.2 The run source seam

`server/source/` is the data-access layer. The run service reads runs only
through one interface:

```ts
interface RunSource {
  listRuns(agent: string, limit: number): Promise<RunSummary[]>;
  getRun(agent: string, runId: string): Promise<RunDetail>;
  readLog(agent: string, runId: string, offset: number): Promise<LogChunk>;
}
```

Phase 1 has one implementation, `launchdLogRunSource` (§3.5). Phase 3 adds an
app-owned source; the API and UI don't change. Agents, schedules and runs use
the Phase 3 names (`Agent`, `Schedule`, `Run`, `RunEvent`) from the start.

## 5. Later phases

### 5.1 Phase 2 — actions over launchd

Buttons for what's done by hand in a terminal today, each a thin wrapper over
the existing script: **Run now** (`agent-schedule-install.sh kick`),
**Pause / Resume** (`launchctl bootout` / `bootstrap` of the existing plist),
**Install** (from the scheduler clone only, which also fixes the wrong-path
mistake), **Remove worktree** (`agent-worktree.sh rm`, clean ones only).
Every mutating request carries an `X-Agent-Orchestrator: 1` header (a
cross-site page can't send it without a CORS preflight the server never
approves); no CORS. Decide at the time whether Run now belongs in the app —
today the user prefers starting runs from their own terminal.

### 5.2 Phase 3 — the app schedules (north star)

The app replaces launchd: schedules in SQLite (`node:sqlite`, DB outside the
repo at `~/.agent-orchestration/`), a cron scheduler, a run queue, live
structured run events, editable schedules. **Deviation from the 2026-09-27
plan:** the app runs **`agent-scheduled-run.sh <agent>`**, not `claude -p`
directly. All the run logic (modes, issue state machine, per-run MCP config,
memory commits, worktrees) already lives in the scripts and keeps working; the
migration is "change who starts the script," not a rewrite. Richer run detail
(tool calls, permission denials, cost) needs `agent-worktree.sh` to also write
`claude`'s `--output-format stream-json` to a file next to the log; that's a
script change, made then.

## 6. Packaging and the pipeline

- Root `CLAUDE.md` §1 lists `agent-web-app/`; §5.5 is its structure section
  (lifting the §1.1 lock); §2's Operational Loop applies to it like the other
  packages.
- **Never built by the pipeline**: `Nyc311PipelineStack`'s synth step only
  runs commands for the packages it names, and `agent-web-app` isn't one.
- **Never triggers the pipeline**: its push trigger excludes
  `agent-web-app/**` alongside `docs/**` (`filePathsExcludes`), so a commit
  touching only this package costs no pipeline run. That exclusion is a
  `cdk/` change with its own test, shipped once through the pipeline.

## 7. Phase 3 design carried over from 2026-09-27

Still the intended design when Phase 3 is built; revisit then:

- **Run rules** — per-schedule max runtime (default 60 min → SIGINT, 30 s
  grace, SIGTERM, `TIMED_OUT`); same schedule still running when due →
  `SKIPPED`; global concurrency cap (default 4) with a FIFO queue; stopping
  the server aborts runs (`ABORTED`), no re-adoption; no catch-up of missed
  runs.
- **Permissions stay in the project, in git** — never
  `--dangerously-skip-permissions`; denials are surfaced with the rule text to
  add through a normal commit.
- **Run modes** — `npm start` is the live instance; a dev mode on another
  port with the scheduler off and a fake runner, so UI work can't affect
  running agents.
- **Retention** — run rows kept; event logs pruned after 30 days.
- **README** — written for any project once the tool schedules agents
  generically.

## 8. Phase 1 build order

1. Root `CLAUDE.md` §1 + §5.5 (review before code).
2. `cdk/` pipeline trigger exclusion + test; Operational Loop in `cdk/`.
3. Scaffold: `package.json`, TS configs, ESLint (`local/comment-format`,
   `jsx-a11y`, 200-line components, no controller → source imports), Vitest
   with the coverage gate, Vite, Tailwind.
4. `shared/models`, then `server/source` readers against `test-data/`
   fixtures (copies of real log shapes, including a failed, a skipped, an
   aborted and a running run).
5. Services (run parsing, health checks, next fire), controllers, `main.ts`.
6. UI: Dashboard → Run (live tail) → Agent → Worktrees.
7. Operational Loop green in `agent-web-app/`.
